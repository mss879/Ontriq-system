# Speed: before and after

Measured on 2026-11-01 from Colombo. These are local results. A signed-in run on the live site follows the deploy.

## What the live site showed before this work

No sign-in, from `scripts/dev/live-probe.sh`. Medians over one reused connection, which is what a browser uses after first load.

| Layer | Time |
|---|---|
| CDN static file | 42 to 79 ms |
| Edge proxy | 48 to 72 ms |
| Function, no database | 145 to 170 ms |
| Function, 2 database reads | 282 to 303 ms |
| Page render, no database | 250 ms |

Six requests at once to `/login`, in ms to first byte: `382 692 4978 4979 5012 5211`. A request that lands on a new function instance waits about 5 seconds.

The first visit to a route on an instance costs about 0.5 s more than a repeat.

Live query stats, one read-only query with the owner's approval: `my_membership` ran 7,220 times at 2.7 ms each in Postgres, the most-called read in the rows reviewed. The `report_versions` read averaged 97 ms, mostly `case_visible()` running once per row.

## A walk through the menu

`scripts/dev/nav-timing.ts` on a local production build, with requests a function would serve held back 250 ms and those a CDN could serve held back 50 ms. Each role opens every menu item, then reopens them all within 30 seconds. Medians.

| | Super Admin | Verification officer | Client admin |
|---|---|---|---|
| Data on a first visit | 597 to 363 ms | 597 to 379 ms | 598 to 364 ms |
| Data on reopening | 363 to 62 ms | 365 to 65 ms | 365 to 65 ms |
| Function calls, whole walk | 44 to 14 | 14 to 4 | 29 to 9 |
| Database calls, whole walk | 188 to 52 | 76 to 22 | 75 to 22 |
| Membership checks, whole walk | 44 to 0 | 14 to 0 | 29 to 0 |

After a hover of 150 ms the screen already changed in about 30 ms before this work. A click on a hover too short for the prefetch to arrive took 280 ms to change the screen, the length of one function call, and now takes 30 ms. On the live site that wait could be a 5 second cold start.

With the server held back 2 seconds, a click shows the page title and skeleton in about 100 ms.

All 45 staff and portal routes carry the static-shell flag. The seven sampled before the change had none.

## Independent review

One independent reader checked the migration and the membership reuse. It compared the old and new rules for every local member at both sign-in levels across all 16 tables, and found two problems. Both are fixed, and every result above is from the final code.

- **`communications`:** `case_id` has no foreign key, so a message can outlive its case. The full-access shortcut made those rows readable to staff with `cases.read`, when before nobody could read them. That policy no longer uses the shortcut. The new test for this failed on the old rule and passes now.
- **Invoice recipients:** the invoice page read recipient emails with the service role on the reused membership, so someone losing `invoices.send` could have seen them for up to a minute. The page now checks the permission fresh.

The other 15 policies matched, and the new functions and their grants came back clean. The reader didn't count orphaned messages on the live database.

## Not yet proved

The app went to GitHub main ahead of migration 0052. `stageCounts()` falls back to counting rows until the migration arrives: with the function hidden locally, the dashboard still showed the same 57 active cases. The case rule speed-up and the SQL stage counts wait for the migration.

These need the deployed site:

- Hover makes no function call for a signed-in person on Netlify.
- How much less often people meet a cold start. Each one still takes about 5 seconds.
- A hidden tab waits for live updates. There is no live-updates server locally.
- Signed-in click timings. The delays above are simulated.
- Whether turning off server source maps shortens cold starts. That needs a comparison between two deploys, so it hasn't been changed.
